# Производительность и нагрузка

Замеры сделаны на production-сборке в Docker (тот же образ, что на стенде) на ноутбуке с Intel Core i5-12450H (12 потоков) и 16 ГБ ОЗУ. База PostgreSQL 16 в соседнем контейнере. Скрипт — `scripts/loadtest.ts`, его можно повторить на любом сервере.

## Требования ТЗ и результат

| Требование | Как мерили | Результат |
|---|---|---|
| 100 пользователей, отклик ≤ 2 с | 100 виртуальных учеников: у каждого своё место ДДС с потоком карточек, опрос состояния места и ленты раз в 1,5 с плюс страница кабинета, 45 с | p95 **0,69 с**, p99 0,94 с, ошибок 0, 132 запроса/с |
| ≥ 20 одновременных сессий | 30 рабочих мест ДДС, у каждого свой поток карточек, опрос раз в секунду, 60 с | p95 **0,23 с**, ошибок 0 |
| ≥ 100 записей/с в БД | 5000 вставок в журнал пачками по 50 | **≈ 5300 записей/с** |
| Отчёт ≤ 30 с | отчёт занятия, выгрузка CSV, сводные отчёты | **0,03–0,07 с** |

Повторный замер 27.09 после всех доработок (адаптивный выбор заданий, прогноз, проверки понятности, удержание звонков): та же production-сборка, 4 процесса, без Docker, тот же ноутбук — 100 рабочих мест: p95 **0,10 с**, p99 0,16 с, 172 запроса/с, ошибок 0 (самый тяжёлый запрос — состояние места ДДС: p95 0,13 с).

**Публичный демо-стенд** (облачный сервер 2 vCPU, 4 ГБ, Санкт-Петербург; 2 процесса приложения; запросы шли через интернет из другого города, с HTTPS): 30 рабочих мест ДДС с опросом раз в секунду, 60 с — p95 **0,49 с**, ошибок 0; 50 мест — p95 2,2 с, ошибок 0: это предел двух ядер. Для класса на 100 мест — сервер из раздела «Требования» (4 ядра, 8 ГБ): на нём сделаны замеры выше.

Команды:

```bash
pnpm exec tsx scripts/loadtest.ts --base http://<сервер>:3000 --users 30 --setup dds --think 1000 --duration 60 --paths /api/dds/state,/api/dds/feed
pnpm exec tsx scripts/loadtest.ts --base http://<сервер>:3000 --users 100 --setup dds --think 1500 --duration 45 --paths /api/dds/state,/api/dds/feed,/student
pnpm exec tsx scripts/loadtest.ts --db-writes 5000
```

## Что для этого сделано

- **Несколько процессов приложения на одном порту** (`cluster.cjs`, переменная `APP_WORKERS`, по умолчанию по числу ядер, но не больше 4). Один процесс Node обрабатывает около 60 запросов опроса в секунду. С четырьмя процессами пропускная способность выросла в 2,4 раза: p95 при 100 рабочих местах упал с 2,4 с до 0,69 с. Фоновые задачи (резервные копии, чистка журнала, сброс демо) выполняет только один процесс.
- **Поток карточек места ДДС двигается не чаще раза в 2 секунды на место**, а счётчики и телефон читаются на каждом опросе. Для таймеров 30 секунд и 3 минуты такой точности хватает с запасом.
- **Пул соединений с базой** — 15 на процесс, всего 60 при лимите PostgreSQL в 100.
- **Шаги места ДДС не падают по таймауту транзакции.** Звонок, удержание, статус и разбор идут в транзакциях с явным ожиданием (до 10 с на соединение, до 20 с на всю транзакцию — в согласии с шагом потока карточек, который держит свою до 15 с), а не с пятью секундами по умолчанию. Ответ на звонок, который уже звенит дольше 25 секунд, не ждёт поток, превращающий его в пропущенный. Если очередь всё же не подошла, API отвечает 503 с понятным текстом «повторите через пару секунд», а опрос места пропускает шаг потока до следующей секунды (`src/lib/dds/tx.ts`).
- Приложение не хранит состояние в памяти между запросами: сессии, очередь карточек и таймеры лежат в базе. Поэтому процессы и серверы можно добавлять без переделок.

## Локальные модели

Замер языковой, распознающей и синтезирующей модели на процессоре и на видеокарте будет добавлен после установки локальных моделей. Сейчас демо-стенд использует облачный API, а без модели тренажёр работает на правилах: см. [methods.md](methods.md).
