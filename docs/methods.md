# Методы обработки данных

Сводка того, как тренажёр принимает решения: что считается правилами по данным заказчика, что делает языковая модель и как из этого получается оценка. Подробности — в документах по частям: [data.md](data.md), [dds.md](dds.md), [op112.md](op112.md), [teacher.md](teacher.md).

## Главный принцип

Всё, от чего зависит правильность, считается правилами по данным заказчика: подбор служб по классификатору и адресу, допустимые переходы статусов, нормативы 30 секунд и 3 минуты, сверка карточки с эталоном. Языковая модель делает только то, что правилами не выразить: играет собеседника (заявителя, старшего бригады, службу), читает свободный текст преподавателя, готовит черновик пояснений к разбору.

Итоговую оценку ставит преподаватель. Черновик идёт в зачёт только после его подтверждения. Если модель недоступна (нет сети, кончился ключ, таймаут), система продолжает работать: собеседник отвечает по фактам сценария правилами, а проверки, которым нужна модель, помечаются «не применимо» и не влияют на балл.

## 1. Справочники заказчика

| Источник | Что получаем | Как |
|---|---|---|
| Классификатор v046_24 (xlsx, 99 колонок, шапка в 3 строки) | 24 группы, 1283 итоговых типа, 21 743 правила маршрутизации | `scripts/convert-classifier.py`: каждая колонка N–CU → пара «группа колонок, условие» (признак не выбран, угроза людям, пострадавшие, нет доступа, газификация, правонарушение, мед. помощь, эвакуация, перекрытие движения и др.) |
| Классификатор v046_11 | «Сценарий реагирования» для 1260 типов | сопоставление по итоговому типу |
| «СЛУЖБЫ 112» | 211 служб окна «Добавьте службы» + 17 скрытых получателей | `scripts/build-services.py`: короткое и полное имя, способ оповещения (АРМ-112, внешняя система, только телефон), округ и район |
| «КАРТОЧКА 112» | 51 значение «что случилось», деревья тегов 101 / 104 / «Взрыв» | ручной разбор скриншотов |
| 32 билета | 96 ситуаций | 15 проработаны вручную вместе с эталоном для ДДС, 81 — черновики |

**Подбор служб** (`src/lib/routing/engine.ts`) — чистая функция от типа, флагов и адреса:

1. Для каждой плашки проверяются её колонки классификатора. Условная подколонка срабатывает, если выбран её признак и в ячейке есть значение, иначе работает «признак не выбран».
2. Территориальные ДДС добавляются по адресу: ДДС района или поселения и ДДС префектуры округа, только если адрес определён до района.
3. Главная служба (столбец M) ставится первой, остальные идут в порядке со скриншотов.

Проверено тестами на всех случаях со скриншотов заказчика и на его примере «пожар в школе в Щукино с пострадавшими» → 101, 102, 103, ЦЭМП, Деп. образования, ДДС Щукино, ДДС СЗАО.

## 2. Сценарии

- **Из билетов** (`scripts/build-scenarios.ts`). Персона заявителя: ФИО, роль, телефон, адрес, который он называет сразу, и скрытый адрес (курсив в билете), который выдаёт только на уточняющий вопрос; факты, которые сообщает только на вопрос. Эталон карточки: тип по классификатору, флаги, службы по движку подбора, обязательные вопросы. Эталон для ДДС: решение за 30 секунд, цепочка статусов, доклад бригады, что должно быть в итоговом комментарии, ловушки.
- **Из свободного текста** (`src/lib/scenarios/generate.ts`, экран «Сценарий из текста»). Эксперт описывает ситуацию своими словами — система собирает черновик. Модель, если подключена, извлекает персону, адрес, флаги и подсказку типа. Затем правила сопоставляют подсказку с листом классификатора: слова совпадают целиком или по основе, «без пострадавших» не путается с «с пострадавшими», лишние уточнения в названии дают штраф. Службы подбирает движок, район — справочник адресов, вопросы — классификатор и типовые вопросы группы.
  - Без модели текст читается правилами по ключевым словам. На 15 проработанных билетах правила определяют тип верно в 14 случаях (правила настраивались на этих же билетах), по всем 96 — в 39. Медицинские и прочие случаи без модели распознаются хуже, их уточняет модель или преподаватель.
- Любой сгенерированный сценарий — черновик. В занятие он попадает только после утверждения преподавателем, целиком или по разделам.

## 3. Собеседники на телефоне

| Кто | Где | Правила поведения |
|---|---|---|
| Заявитель | место 112 | говорит видимый адрес, истинный — только на уточняющий вопрос; факты — только если спросили; манера по характеру (паника, пожилой, ребёнок) |
| Старший бригады | место ДДС | сам звонит на каждом этапе: выехали, прибыли, работы, итог; отвечает, когда диспетчер звонит сам |
| Заявитель при перезвоне | место ДДС | отвечает по фактам сценария, номер карточки не знает |

Промпты написаны под задачу 112 и ДДС. Без модели ответы строятся по фактам сценария: ключевые слова вопроса → нужный факт. Голос — нажми-и-говори: речь распознаётся сервером или браузером, ответ озвучивается мужским или женским голосом по персоне.

## 4. Оценка

**Проверки.** Каждая проверка возвращает результат: пройдена, провалена или не применима, с доказательством (время, цитата, статус) и правильным действием. Проверки разбиты на 7 групп: время, порядок статусов, комментарии и «кому передано», адрес, тип и службы, полнота, понятность текста.

- Место ДДС: 15 проверок по каталогу нарушений из памятки — ответ за 30 секунд, наряд за 3 минуты, статусы по докладам бригады не позже минуты, итоговый статус, итог в комментарии, «кому передано» при отказе, решение по эталону и др. Подробно — [dds.md](dds.md).
- Место 112: сверка «сказал заявитель ↔ заполнил оператор» с цитатами, адрес (улица-двойник — критическая ошибка), тип, флаги, службы, обязательные поля и вопросы, суть в первых 100 символах описания, время набора карточки. Подробно — [op112.md](op112.md).

**Балл** — взвешенная доля пройденных проверок:

```
балл = Σ по группам ( вес группы × пройдено в группе / применимо в группе ) / Σ весов групп, где есть применимые проверки
```

«Не применимо» в знаменатель не входит, поэтому пустая попытка не получает 100 %. Проваленная критическая проверка ограничивает балл 40 %. Сырые результаты хранятся в попытке, поэтому смена весов на панели преподавателя мгновенно пересчитывает все попытки. Жюри может само крутить веса.

**Черновик → решение преподавателя.** Преподаватель подтверждает черновик («Верно») или исправляет отдельные проверки с комментарием («ИИ неправ»). Правка пишется в журнал аудита: кто, когда, было, стало. В отчёты и кабинет обучающегося идут только подтверждённые попытки. Доля проверок, где преподаватель согласился с черновиком, показывается в отчёте — это мера качества автоматической оценки.

## 5. Отчёты и выводы по группе

Всё считается по подтверждённым попыткам:
- время против норматива по каждому ученику;
- лидеры и отстающие с причинами — какие проверки чаще проваливались;
- типичные ошибки группы одной фразой («сегодня все валятся на адресе и на отказе без комментария»);
- тепловая карта «ученик × группа проверок»;
- уровни готовности по среднему баллу: 85 / 70 / 50.

Выгрузка — CSV для Excel.

## 6. Что сознательно не делает ИИ

- Не ставит итоговую оценку и не спорит с преподавателем.
- Не решает, какие службы должны быть в карточке: это классификатор заказчика.
- Не меняет утверждённые сценарии: переписанный ИИ раздел снова становится черновиком.
- Не видит персональных данных за пределами учебного занятия.
